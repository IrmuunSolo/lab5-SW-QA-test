## 1. Зорилго ба хамрах хүрээ

Лекцийн тест дизайны таван алхмыг хичээлд бүртгүүлэх REST API дээр хэрэгжүүлэв: бие даан тестлэгдэх функц сонгох, оролтын сонголтууд тодорхойлох, төлөөлөх утгууд сонгох, спецификаци боловсруулах, бодит тест кейс бүтээх. Гол тестлэгдэх функц нь `POST /registrations` юм. `PUT /students/:id`, `PUT /courses/:id` endpoint-уудыг тест бүрийн setup-д ашигласан.

Тестүүд хэвийн бүртгэл, дөрвөн үндсэн алдааны анги, давхар алдааны хоёр хослол, урьдач нөхцөлгүй хичээл, хоосон үзсэн хичээлийн массив, талбар дутуу болон буруу JSON оролтыг хамарна. GET endpoint-ууд болон нэмэлт нийтийн API туршилтыг энэ collection-д оруулаагүй.

## 2. Сонголт ба төлөөлөх утгын хүснэгт

| Сонголт | Эквивалент анги | Төлөөлөх утга |
|---|---|---|
| Оюутны төлөв | Байгаа, идэвхтэй | `status: "active"` |
| Оюутны төлөв | Байгаа, идэвхгүй | `status: "inactive"` |
| Оюутны төлөв | Байхгүй | PUT-аар үүсгээгүй `S02_missing` |
| Хичээлийн төлөв | Байгаа | PUT-аар үүсгэсэн `CS313` |
| Хичээлийн төлөв | Байхгүй | PUT-аар үүсгээгүй `C04_missing` |
| Урьдач нөхцөл | Бүгдийг үзсэн | Шаардлага `["CS201"]`, үзсэн `["CS201"]` |
| Урьдач нөхцөл | Огт үзээгүй | Шаардлага `["CS201"]`, үзсэн `[]` |
| Урьдач нөхцөл | Заримыг үзсэн | Шаардлага `["CS201","CS202"]`, үзсэн `["CS201"]` |
| Урьдач нөхцөл | Урьдач нөхцөлгүй | `prerequisites: []` |
| Хүсэлтийн бүтэц | Хоёр талбар байгаа | `studentID`, `courseID` хоёулаа байна |
| Хүсэлтийн бүтэц | Талбар дутуу | `courseID` байхгүй |
| JSON формат | Зөв | Хүчинтэй JSON объект |
| JSON формат | Буруу | Төгсгөлийн `}` хаалт дутуу |

Байхгүй оюутныг нэгэн зэрэг идэвхгүй гэж ангилах боломжгүй; идэвхгүй төлөв нь байгаа бичлэгийн шинж юм. Байхгүй хичээлийн урьдач нөхцөл хангагдсан эсэхийг мөн тодорхойлох боломжгүй. Урьдач нөхцөлгүй хичээлд “зарим урьдачийг үзсэн” гэсэн анги утгагүй тул тусдаа амжилтын хязгаарын тохиолдол болгон сонгосон.

## 3. Тестийн спецификаци

| ID | Оролт ба нөхцөл | Хүлээгдэх HTTP статус | Хүлээгдэх `result` | Нэмэлт oracle |
|---|---|---:|---|---|
| T01 | `B231234567` идэвхтэй, CS201 үзсэн; CS313 нь CS201 шаарддаг | 201 | `OK` | `registrationID` тоо |
| T02 | `S02_missing` байхгүй, C02 байгаа | 200 | `ERROR_NO_STUDENT` | — |
| T03 | S03 идэвхгүй, C03 байгаа | 200 | `ERROR_INACTIVE_STUDENT` | — |
| T04 | S04 идэвхтэй, `C04_missing` байхгүй | 200 | `ERROR_NO_COURSE` | — |
| T05 | S05-ийн `coursesTaken: []`; C05 нь CS201 шаарддаг | 200 | `ERROR_PREREQUISITES` | `missing: ["CS201"]` |
| T06 | `S06_missing`, `C06_missing` хоёулаа байхгүй | 200 | `ERROR_NO_STUDENT` | Давхар алдааны дараалал |
| T07 | S07 идэвхгүй, `C07_missing` байхгүй | 200 | `ERROR_INACTIVE_STUDENT` | Давхар алдааны дараалал |
| T08 | S08 идэвхтэй, CS201 үзсэн; C08 урьдач нөхцөлгүй | 201 | `OK` | `registrationID` тоо |
| T09 | S09 идэвхтэй, `coursesTaken: []`; C09 урьдач нөхцөлгүй | 201 | `OK` | `registrationID` тоо |
| T10 | S10 зөвхөн CS201 үзсэн; C10 нь CS201, CS202 шаарддаг | 200 | `ERROR_PREREQUISITES` | `missing: ["CS202"]` |
| T11 | POST body-д `studentID: "S11"` байгаа, `courseID` байхгүй | 400 | `ERROR_BAD_REQUEST` | — |
| T12 | S12, C12 ашигласан POST body-ийн төгсгөлийн хаалт дутуу | 400 | `ERROR_BAD_JSON` | — |

T06-д оюутан байхгүй гэсэн алдаа, T07-д идэвхгүй оюутны алдаа эхэлж буцсаныг туршилтаар баталгаажуулсан. Эдгээр нь зааварт дарааллыг урьдчилан тогтоогоогүй давхар алдааны тохиолдлууд бөгөөд серверийн одоогийн зан төлөвийг харуулна.

## 4. Collection-ийн бүтэц ба бие даасан байдал

[Зөв collection](lab05-collection.json) нь T01–T12 гэсэн 12 folder-той. Folder бүр дараах гурван хүсэлтийг дарааллаар ажиллуулна:

1. `PUT /students/:id` — оюутны setup.
2. `PUT /courses/:id` — хичээлийн setup.
3. `POST /registrations` — тестлэгдэх үйлдэл.

Folder бүр өөрийн setup-тай, бусад тестийн үүсгэсэн бичлэгт найдахгүй. Байхгүй ID шалгах тохиолдолд `_fixture` ID-тай тусдаа setup бичлэг үүсгэж, POST-д PUT-аар үүсгээгүй `_missing` ID ашиглана. Collection-ийн аль ч setup `_missing` ID үүсгэдэггүй.

Collection variable `baseUrl` нь `http://localhost:3000` бөгөөд экспортолсон JSON-д хадгалагдсан. Хүсэлтүүд `{{baseUrl}}` ашиглана. JSON body-той хүсэлтүүдийн `Content-Type` нь `application/json` юм.

PUT хүсэлт бүр HTTP 200 болон `result: "OK"` гэсэн хоёр assertion-той. POST хүсэлт бүр статус ба `result`-ийг шалгана. T01, T08, T09-д `registrationID` тоо эсэхийг, T05, T10-д дутуу урьдачийн массивыг нэмж шалгана. Сервер in-memory тул бүртгэлийн ID хуримтлагддаг; `registrationID == 1` гэх мэт яг утгаар шалгаагүй.

| Бүрэлдэхүүн | Assertion-ы тоо |
|---|---:|
| 24 PUT setup × 2 | 48 |
| 12 POST × 2 | 24 |
| 3 амжилтын `registrationID` шалгалт | 3 |
| 2 `missing` массивын шалгалт | 2 |
| **Нийт** | **77** |

**12 сценарио, 36 HTTP хүсэлт, 77 assertion** нь өөр өөр тооллого юм. Тайлангийн тестийн шалгалтын тоо нь Newman-ийн `assertions executed` мөртэй таарах 77 байна.

## 5. Суулгах ба ажиллуулах

Репозиторийг татаж, үндсэн хавтсанд орно:

```bash
git clone https://github.com/IrmuunSolo/lab5-SW-QA-test.git
cd lab5-SW-QA-test
```

`package.json`, `package-lock.json`-д бүртгэсэн dependency-г суулгана:

```bash
npm ci
node -v
npx newman -v
```

Сервер нь Node.js-ийн үндсэн `http` модулийг ашигладаг тул өөрөө нэмэлт сан шаардахгүй. Terminal 1 дээр серверийг ажиллуулна:

```bash
node server.js
```

Серверийн гаралт:

```text
Бүртгэлийн API: http://localhost:3000
```

Дараах Newman командуудыг Terminal 2 дээр, репозиторийн үндсэн хавтсанд Bash-аар ажиллуулна. `run_exit=${PIPESTATUS[0]}` мөрийг pipeline-ийн яг дараа ажиллуулж Newman-ийн exit code-ыг авна; дан `$?` нь `tee`-ийн код болж болно.

### 5.1 PASS — зөв collection

Сервер ажиллаж байх үед:

```bash
mkdir -p results
npx newman run lab05-collection.json 2>&1 | tee results/newman-pass.txt
run_exit=${PIPESTATUS[0]}
printf 'exit=%s\n' "$run_exit" | tee -a results/newman-pass.txt
```

### 5.2 FAIL — зориуд буруу oracle

Сервер ажиллаж байх үед тусдаа collection ажиллуулна:

```bash
npx newman run lab05-collection-fail.json 2>&1 | tee results/newman-fail.txt
run_exit=${PIPESTATUS[0]}
printf 'exit=%s\n' "$run_exit" | tee -a results/newman-fail.txt
```

### 5.3 DOWN — сервер унтарсан

Terminal 1 дээр `Ctrl+C` дарж серверийг зогсооно. Дараа нь Terminal 2 дээр зөв collection ажиллуулна:

```bash
npx newman run lab05-collection.json 2>&1 | tee results/newman-down.txt
run_exit=${PIPESTATUS[0]}
printf 'exit=%s\n' "$run_exit" | tee -a results/newman-down.txt
```

## 6. Бодит үр дүн ба нотолгоо

| Ажиллуулалт | Requests executed | Requests failed | Assertions executed | Assertions failed | Exit code |
|---|---:|---:|---:|---:|---:|
| PASS | 36 | 0 | 77 | 0 | 0 |
| FAIL | 36 | 0 | 77 | 1 | 1 |
| DOWN | 36 | 36 | 77 | 77 | 1 |

Бүтэн текст гаралтууд:

- [PASS — newman-pass.txt](results/newman-pass.txt)
- [FAIL — newman-fail.txt](results/newman-fail.txt)
- [DOWN — newman-down.txt](results/newman-down.txt)

### PASS

Зөв collection-ийн 77 assertion бүгд амжилттай, хүсэлтийн алдаа байхгүй, `exit=0` гарсан. Энэ нь сонгосон 12 сценариогийн oracle-уудтай бодит хариунууд тохирсныг харуулна.

### FAIL

[Буруу oracle-тай collection](lab05-collection-fail.json)-ийн T01 POST хүсэлтэд HTTP 201-ийн оронд 200 хүлээхээр ганц статусын oracle-г өөрчилсөн. Үндсэн collection-ийн зөв oracle хэвээр байна. Унасан assertion:

```text
Зориуд буруу oracle: статус 200 байна
expected response to have status code 200 but got 201
```

Бүх 36 хүсэлт сервертэй амжилттай холбогдсон боловч 77 assertion-оос нэг унаж, `exit=1` гарсан. Энэ нь буруу хүлээгдэж буй утгатай oracle-г илрүүлж, автомат ажиллуулалтыг амжилтгүй төлөвөөр дуусгасныг харуулна.

### DOWN

Серверийг зогсоосны дараах гаралтад:

```text
connect ECONNREFUSED 127.0.0.1:3000
```

гэсэн мөрүүд байна. 36 хүсэлт бүгд холболтын алдаатай болж, 77 assertion бүгд унаж, `exit=1` гарсан. Хариу ирээгүйгээс статус ба JSON шалгалтууд дагалдан унасан.

**FAIL нь хариу ирсэн боловч зориуд буруу oracle-тай тохироогүй алдаа; DOWN нь серверт холбогдож чадаагүй интерфейсийн алдаа юм.**

## 7. Дүгнэлт

Энэ лабораторийн ажлаар тест дизайны таван алхмыг ашиглан хичээлд бүртгүүлэх API-д 12 сценарио боловсруулсан. Хамгийн их бодол шаардсан алхам нь сонголтуудыг хослуулж, давхар алдааны хүлээгдэж буй үр дүнг тодорхойлох спецификаци боловсруулах үе байв. Байхгүй оюутныг идэвхгүй гэж зэрэг ангилах болон байхгүй хичээлийн урьдач нөхцөлийг үнэлэх нь утгагүй хослол болохыг ялгасан. Тест бүр өөрийн PUT setup-тай тул өмнөх тестийн үүсгэсэн өгөгдөлд найдахгүйгээр нөхцөлөө бэлтгэдэг. Давхар алдааны туршилтаар оюутан байхгүй болон идэвхгүй гэсэн шалгалтууд хичээл байхгүй гэсэн шалгалтаас өмнө хэрэгждэгийг баталгаажуулсан. PASS ажиллуулалтаар 36 хүсэлт, 77 assertion алдаагүй дууссан бөгөөд сонгосон тохиолдлуудад серверийн шаардлагын зөрчил илрээгүй. registrationID-ийн яг утгыг шалгаагүй нь серверийн санах ойд бүртгэл хуримтлагдах үед тест дахин ажиллах боломжийг хангана. HTTP 201-ийг зориуд 200 гэж хүлээсэн FAIL туршилтаар нэг assertion унаж, exit code 1 гарсан нь oracle-ийн алдааг илрүүлснийг харуулсан. Сервер унтарсан DOWN туршилтын ECONNREFUSED нь буруу хариунаас бус холболтгүй интерфейсээс үүссэн алдаа болохыг ялгасан. Иймээс амжилттай ажиллуулахын зэрэгцээ зориуд унагаах болон холболтгүй нөхцөлийг шалгах нь тестийн нотолгоог илүү тодорхой болгодог гэж дүгнэв.
